# 06. 詳細設計

機能設計（FUNC-XXX）・DB設計（テーブル）・画面設計（画面）を踏まえ、内部処理（API・ロジック）を具体化する。各APIには関連FUNCを明記する。

## API一覧
| ID | Method/Path | 概要 | 関連FUNC |
|---|---|---|---|
| API-01 | POST `/api/auth/login` | email+passwordを検証し、`iron-session`にセッションを保存 | FUNC-001 |
| API-02 | POST `/api/auth/logout` | セッションを破棄 | FUNC-002 |
| API-03 | GET `/api/projects` | ログインユーザーのプロジェクト一覧＋各フェーズの進捗概要を返す | FUNC-011 |
| API-04 | POST `/api/projects` | プロジェクトを作成し、8フェーズをトランザクションでseedする | FUNC-010, FUNC-013 |
| API-05 | DELETE `/api/projects/[projectId]` | プロジェクトを削除（カスケードで全データ削除） | FUNC-012 |
| API-06 | GET `/api/projects/[projectId]/phases/[phaseType]` | そのフェーズのチャット履歴＋成果物を返す（phaseGuardで未到達ならエラー） | FUNC-040 |
| API-07 | POST `/api/projects/[projectId]/phases/[phaseType]/chat` | ユーザー発言を保存→Claudeにストリーミングで問い合わせ→応答を保存 | FUNC-020, 021, 023, 025 |
| API-08 | PATCH `/api/projects/[projectId]/phases/[phaseType]/deliverable` | 成果物の手動編集（構造化リストの項目追加/編集/削除、ER図テキスト編集、ワイヤーフレーム要素編集、画面遷移図テキスト編集、チェックリストのdone切替）。対象フェーズが既に`DONE`/`NEEDS_REVIEW`（＝確定済み）だった場合、API-09と同じ下流カスケードを実行する（チェックリストのdone切替のみは例外、下記参照） | FUNC-022, 031, 041, 061, 063, 065 |
| API-09 | POST `/api/projects/[projectId]/phases/[phaseType]/finalize` | フェーズを確定し、ステータスをDONEに。下流フェーズがDONEなら`NEEDS_REVIEW`にカスケード。TEST_DESIGN確定時はIMPLEMENTATION_CHECKLISTを自動生成して直接DONEにする | FUNC-024, 030, 041 |

| API-12 | POST `/api/projects/[projectId]/phases/SCREEN_DESIGN/design-image` | 画面名＋（任意で）フィードバックを受け取り、OpenAI画像生成APIで画像を生成/編集し`designImages`に保存 | FUNC-066, 067 |

## 主要処理フロー

### フェーズ遷移制御（phaseGuard）
- `ensurePhaseUnlocked(projectId, phaseType)`: 対象より`order`が小さい全Phaseが`DONE`または`NEEDS_REVIEW`であることを確認する（`NEEDS_REVIEW`でも先には進める。内容の再確認を促すだけで進行自体はブロックしない）。満たさない場合、最も手前の未完了フェーズにリダイレクトする。
- API-06, API-07, API-08, API-09はすべてこのガードを通す。

### チャット送信〜finalize提案（API-07）
1. ユーザー発言を`ChatMessage`に保存。
2. そのフェーズの履歴＋前フェーズまでの確定済み`Deliverable.content`を文脈として構築。
3. Claudeへストリーミングでリクエスト（フェーズ別システムプロンプト使用）。項目提案はテキスト応答の一部として自然文で行い、ユーザーがFUNC-021の操作でリストに反映する。
4. Claudeの応答に「確定してよさそう」という判断が含まれる場合、構造化出力で`readiness: "ready"`を返させ、UIに確定提案バナー（FUNC-023）を表示する。
5. 応答をストリーム完了後に`ChatMessage`として保存。

### 直接編集時のカスケード（API-08）
確定済み（`isFinal: true`）の`Deliverable`をチャット・finalizeを経由せず直接編集した場合も、「内容が変わった」という点では再確定と同じなので、下流フェーズへのカスケードは共通化する: 更新処理の中で「対象フェーズが`DONE`または`NEEDS_REVIEW`だったか」を判定し、真であれば下記「フェーズ確定」フローの手順3（要見直しカスケード）だけを追加で実行する（手順1・2・4は再実行しない。ステータス自体は変更せず`DONE`のまま維持してよい）。ただし`IMPLEMENTATION_CHECKLIST`フェーズの`done`切替（FUNC-031）は対象外とする（最後のフェーズであり、チェックの付け外しは実装進捗の記録そのものなので、これをもって「下流に影響がある変更」とは扱わない）。

### フェーズ確定（API-09）
1. 現在の構造化リスト／ワイヤーフレーム／ER図の内容を`Deliverable`としてupsert（`isFinal: true`, `version`+1）。
2. `Phase.status`を`DONE`に更新。次フェーズ（`order+1`）が`NOT_STARTED`なら`IN_PROGRESS`に。
3. それより`order`が大きく、既に`DONE`だったフェーズをすべて`NEEDS_REVIEW`に更新（要見直しカスケード、FUNC-041）。
4. `phaseType === TEST_DESIGN`の場合、続けてIMPLEMENTATION_CHECKLISTの自動生成処理（下記）を実行し、そのPhaseを直接`DONE`にする。

### 実装TODOチェックリスト自動生成（FUNC-030）
1. FUNCTIONAL_DESIGN・DETAILED_DESIGN・TEST_DESIGNの確定済み`Deliverable.content`をまとめてClaudeに渡す。
2. 機能設計の各項目（FUNC的な項目）に対応するTODO項目を構造化出力で生成（`relatedFunctionalItem`に機能設計側のIDを入れる）。
3. `CHECKLIST`形式の`Deliverable`として保存し、`IMPLEMENTATION_CHECKLIST`フェーズを`DONE`にする（チャットは発生しない）。

### 整合性チェック（API-11）
1. そのプロジェクトで`DONE`な全Phaseの`Deliverable.content`を取得し、フェーズ名付きでテキスト化して連結。
2. Claudeに「矛盾点を指摘して」という指示とともに渡し、`{ findings: [{ severity, phasesInvolved, description, suggestion? }], summary }`を構造化出力で取得。
3. `ConsistencyCheck`として保存し、実行履歴として複数回分残す（最新を画面にはデフォルト表示）。

### デザインイメージ生成・ブラッシュアップ（API-12）
1. SCREEN_DESIGNフェーズのチャット中、ユーザーが見た目について要望を述べると、Claudeが`generate_design_image`ツールを呼び出し、`{ screenName, imagePrompt }`を返す（`imagePrompt`はClaudeが要望をまとめた説明文）。
2. サーバー側で、対象`screenName`の現在のワイヤーフレーム要素をテキスト化したもの＋`imagePrompt`＋（任意）企画フェーズのコンセプトからの一言トーンを合成し、最終的な画像生成プロンプトを組み立てる。
3. 既にその画面の`designImages`に画像が存在する場合はOpenAIの画像編集（image edit/多ターン生成）で前回画像をベースに更新、存在しない場合は新規生成する。
4. 結果（`imageBase64`）と使用した`prompt`を`WIREFRAME.content.designImages`の該当`screenName`エントリにupsertする。
5. この処理はfinalizeを経由せず即時保存され、下流フェーズへのNEEDS_REVIEWカスケードは発生しない（FR-9）。

### 成果物のMarkdown変換（API-13, FUNC-068/069）
- `Deliverable.format`ごとに専用の変換関数を持つ（`lib/deliverableToMarkdown.ts`）: STRUCTURED_LISTは項目を見出し＋箇条書きに、ER_DIAGRAMは````mermaid`コードブロックに、WIREFRAMEは画面ごとの要素を箇条書き＋画面遷移図のコードブロックに（デザインイメージはMarkdown中には埋め込まず「画像は別途アプリ内で確認」の注記のみ）、CHECKLISTはチェックボックス付きリスト（`- [x] / - [ ]`）に変換する。
- この変換はDB保存せず、表示・コピーの都度オンデマンドで行う。前フェーズ文脈の引き渡し（FR-3）・整合性チェック（API-11）・デザインイメージ生成（API-12）で必要な「構造化データのテキスト化」も、同じ変換関数を共通利用する。

### 要見直しの解消（FUNC-042）
- 通常のフェーズ（STRUCTURED_LIST/ER_DIAGRAM/WIREFRAME）: `NEEDS_REVIEW`のフェーズを開き、内容を確認した上で「問題なし」ボタンで`DONE`に戻すか、修正して再度finalizeする（再度finalizeした場合は上記「フェーズ確定」フローが再実行され、さらに下流が`NEEDS_REVIEW`になる）。
- IMPLEMENTATION_CHECKLISTが`NEEDS_REVIEW`になった場合（上流の再確定・直接編集によるカスケード）: チャットが無いため、ユーザーは「問題なし」（内容を変えず`DONE`に戻す）か「再生成」のいずれかを選ぶ。「再生成」を選んだ場合は以下のマージ処理を行い、チェック済みの実装進捗を失わないようにする。
  1. FUNCTIONAL_DESIGN・DETAILED_DESIGN・TEST_DESIGNの最新の確定済み内容から、TODO項目候補を生成（FUNC-030と同じ生成処理）。
  2. 既存の`CHECKLIST.content.items`と、生成し直した候補を`relatedFunctionalItem`（機能設計側のID）で突き合わせる。
  3. IDが一致する項目は、既存の`done`の値をそのまま引き継ぐ（タイトルや説明文が変わっていても`done`は保持）。
  4. 候補側に新しく現れたID（対応する既存項目が無い）は`done: false`で追加する。
  5. 既存側にあって候補側に無くなったID（機能設計などから該当項目が削除された）は一覧から取り除く。
  6. マージ後の内容で`CHECKLIST` Deliverableを更新し、`IMPLEMENTATION_CHECKLIST`のステータスを`DONE`に戻す。

## フェーズ別ヒアリング観点（readiness判定基準）
各フェーズのシステムプロンプトは、単に「質問を重ねる」のではなく、以下の観点チェックリストを埋めることを目標にする。**必須**項目がすべて十分に埋まっていれば、Claudeは`propose_finalize`で`readiness: "ready"`を返してよい（**任意**項目は埋まっていなくても確定を提案できる）。

### 企画
- 必須: サービス名／背景・課題／コンセプト／ターゲットユーザー／ゴール・成功基準／非対象
- 任意: 差別化ポイント／開発体制・制約／将来的な拡張

### 要件定義
- 必須: 機能要件一覧（各項目に優先度Must/Should/Couldを付与）
- 任意: 非機能要件／制約条件／優先度の方針の明文化
### 機能設計
- 必須: 要件定義の各FRに対応する機能（FUNC）が最低1つ存在し、ID・概要・関連FRが明記されていること
- 任意: 機能のグルーピングの綺麗さ、粒度の細かさ（詳細設計で分割し直してもよい）
### 画面設計
- 必須: 機能設計の各機能（FUNC）がどこかの画面に対応づけられていること（網羅性）、各画面の主要な要素構成、画面遷移図（画面同士のつながり）
- 任意: デザインイメージ（画面ごとの参考画像、OpenAIで生成・ブラッシュアップ。無くても確定できる）
### DB設計
- 必須: 画面設計で出てきた各画面の入力・表示項目が、どこかのテーブル・カラムに対応していること（網羅性）、エンティティ同士の関係（外部キー）
- 任意: カラムの型の細かい最適化、インデックス設計、正規化の厳密さ
### 詳細設計
- 必須: 機能設計の各機能（FUNC）に対応するAPI・処理が最低1つ存在すること（網羅性）、複雑な分岐がある処理のフロー
- 任意: エラーハンドリングの細部、外部連携の実装詳細
### テスト設計
- 必須: 機能設計／詳細設計の各項目（FUNC・API）に対応するテストケースが最低1つ存在すること（網羅性。実装TODOチェックリストの生成元になるため特に重要）
- 任意: 異常系・エッジケースの細かさ、手順の詳細さ

## Claude API連携の詳細
- フェーズごとのシステムプロンプト・Zodスキーマは`PHASE_CONFIG`（`lib/phases.ts`）に集約する。
- 各フェーズのシステムプロンプトは上記「フェーズ別ヒアリング観点」のチェックリストを埋め込み、`propose_finalize`ツールの判断基準として明示する。
- SCREEN_DESIGNフェーズのみ追加で`generate_design_image`ツールを持ち、見た目の要望をまとめて画像生成プロンプトを提案する（実際の画像生成はClaudeではなくOpenAIが行う。サーバー側の環境変数`OPENAI_API_KEY`を使用）。
- チャット（API-07）は`messages.stream()`、finalize（API-09）・整合性チェック（API-11）・TODO生成は`messages.parse()` + `output_config.format`で構造化出力を使う。
- モデルはClaude Opus 5.5固定。整合性チェックのように複数文書を跨いだ推論が必要な処理は`effort: "high"`を指定する。

## エラーハンドリング方針
- Claude API呼び出し失敗（キー未設定・レート制限等）はAPIが4xx/5xxを返し、UIはトースト等で「AIとの通信に失敗しました」とだけ表示する（詳細なエラーメッセージは画面に出さない）。
- OpenAI画像生成API呼び出し失敗時も同様に、UIで「画像生成に失敗しました」とだけ表示する。失敗してもワイヤーフレーム本体やチャットには影響しない（デザインイメージはあくまで参考情報のため）。
- `phaseGuard`で弾かれた場合は、エラーではなく正常なリダイレクトとして扱う。
- Mermaidの構文エラーはクライアント側でcatchし、ER図表示エリアにインラインでエラー表示する（API呼び出しは発生しない）。
